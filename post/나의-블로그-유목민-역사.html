나는 정말 많은 블로그를 개발하고 옮겨다녔다. GitHub Pages 블로그를 만들게된 기념으로, 나의 블로그 활동 역사를 한 번 소개해보도록 하겠다.

나의 블로그 유목민 역사가 개인 블로그를 운영하고 싶은 개발자분들께 조금이나마 도움이 되기를 바란다.

Blog Haneum

GitHub Repo: https://github.com/chebread/blog-haneum

2021년에 처음으로 HTML와 CSS를 배우고 나서, Blog Haneum이라는 정적 블로그를 만들었다. 블로그 마크업 구조, 블로그 본문 CSS 등 모든 부분을 내가 개발했다. 하나하나 개발하면서 즉각적으로 시각적인 결과물이 보여서 정말 재미있었다. 이 블로그 개발로 하여금 웹 개발에 본격적으로 흥미가 생겼던 것 같다.


이 블로그를 스타일링 하면서 아직도 기억나는 것은, 그 당시 Clubhouse가 유행하던 때라 클럽 하우스의 기술 블로그를 참고해서 위 이미지처럼 메뉴 팝업을 꾸몄었다.

Velog

Link: https://velog.io/@haneum

Blog Haneum 블로그를 통해 포스팅을 했지만 Read only만 되는지라, 독자들과 상호작용을 할 수 없었다. 그때 Velog라는 서비스에 대해서 알게 되었다. Velog에는 댓글 기능이 자체적으로 탑재되어 있어서 독자들과 상호작용을 할 수 있었다. 그래서 2022년에 Velog를 개설하고 포스팅을 하기 시작했다.

내가 처음으로 쓴 힙하게 코딩하는 방법 포스팅이 게시한 지 일주일도 안되서 피드 상위에 랭크되고, 좋아요가 80개에 육박하여 너무 재밌었던 기억이 아직도 남아있다.

글 작성 당시에는 중학생이었어서, 비판적인 댓글에 대해서 불쾌함을 느껴 반박하는 댓글도 남기기도 했다. 그 당시 나는 개발자 문화인 '비판'에 대해서 아예 몰랐었다. 그 이후, 나는 지속적으로 개발을 하면서 비판에 대해 생각이 많이 바뀌었다. 개발자에게 비판이란 인격 모독이 아니라, 나를 성장케 하는 양분이라는 것을 점차 알게 되었다.

Haneum Blog

GitHub Repo: https://github.com/chebread/haneum-blog

Velog에서 활동을 하게 되면서 많은 개발자분들의 벨로그를 많이 보게 되었다. Velog를 보면서 다수의 개발자분들이 개인 사이트를 가지고 계신다는 사실을 알게 되었다. 그래서 나는 나를 소개하는 웹 사이트의 필요성에 대해서 지각하게 되었다.

그 당시 나는 React를 통해 SPA(Single Page Application)를 배우고 있었다. React 자체는 매우 쉬웠지만, SPA의 핵심 동작 방식은 잘 알지 못했다. SPA의 핵심 동작과 ES6의 문법도 익힐겸 Haneum Blog라는 개인 블로그를 직접 만들어보기로 했다.

이 블로그를 개발할 때는 SPA를 직접 구축하는 것이 목표다보니, CRA(Create React App)의 도움을 받지 못했음으로 직접 이렇게 Webpack과 Babel을 구성했었다. 지금은 Vite 같은 도구들이 워낙 잘나오는 편이라 이런 웹 개발 환경을 구성하는 것이 매우 생소할 수 있으나, 그땐 그랬다.

const config = webpackConfig('production');
const configWithSmp = new SpeedMeasurePlugin().wrap(config);
configWithSmp.plugins.push(
  new MiniCssExtractPlugin({
    filename: '[name].[hash:8].css',
    chunkFilename: '[name].[hash:8].chunk.css',
  })
);
const compiler = webpack(configWithSmp);
fs.emptyDirSync(paths.appBuild);
fs.copySync(paths.appPublic, paths.appBuild, {
  dereference: true,
  filter: file => file !== paths.appHtml,
});
const build = () => {
  compiler.run();
};
build();

그리고 이렇게 window 객체를 활용해서 SPA 라우터를 구현해보기도 했다.

import routes from './routes.js';
import render from './render.js';

const router = path => {
  if (!(path === window.location.pathname)) {
    window.history.pushState(null, null, window.location.origin + path);
  }
  if (!routes[path]) {
    if (!(path === '/')) {
      render('/404');
    }
    return;
  }
  render(path);
  window.onpopstate = () => {
    if (!routes[window.location.pathname]) {
      if (!(window.location.pathname === '/')) {
        render('/404');
      }
      return;
    }
    render(window.location.pathname);
  };
};

export default router;

SPA를 구현하는데 있어서, 라우터가 가장 구현하기 힘들었다. 라우터가 SPA의 핵심이었음으로, 일단 라우터가 만들어져야 SPA 사이트를 만들 수 있었다. 그래서 거의 몇 주 동안은 라우터만 개발하고 개선했던 거 같다. 그 당시에는 JavaScript도 잘 익히지 못했던 터라, 구현하는데 정말 힘들었다. SPA를 직접 개발하면서, SPA 프레임워크/라이브러리를 쓰는 이유를 몸소 알게 되었다.

나는 이론과 실전은 항상 병행해야 한다고 생각한다. 이론만 공부한다면, 실전에서 어떻게 이론을 활용해야 하는지 감도 오지 않는다. 쳇바퀴 처럼 이론만 공부하는 사람이 되어 버린다. 그러나 실전만 한다면, 또 이론은 알지 못한다. 실전만 하다가 언제부터 이론의 필요성을 느껴 이론을 공부하게 되면 너무 어려운 탓에 이론 공부를 도외시하게 되기 십상이다. 그래서 내가 추천하는 방법은 이론과 실전을 병행하는 것이다. Haneum Blog도 SPA를 공부하기 위해 진행한 프로젝트이고, 정적 사이트 빌더도 Go 언어의 슬라이스를 익히고자 진행한 프로젝트이다. 여담이지만, 난 어렸을 때 레고를 참 좋아했는데 레고 설명서를 보고 일단 만든 후 부셔버리고 새로운 걸 창작하는 것을 참 좋아했다. 이러한 내 유년시절의 경향성이, 지금 이렇게 프로그래밍에서도 발현되는듯 하다.

thisishaneum

Haneum Blog 블로그를 만들었지만, 내가 완벽주의 성향이 있는지라 약간 부족하다고 생각되어 thisishaneum라는 새로운 개인 사이트를 만들게 되었다. 해당 사이트는 블로그의 성격보다는, 나를 표현하는 것에 더욱더 초점을 맞춰 개발하고자 했다.

그 당시 나는 React를 학습하고 있었음으로 React를 기반하여 thisishaneum를 만들게 되었다. 그러나, React로 이 사이트를 만드는 것은 매우 어려움이 많았다. Horizontal scroll을 구현하기 위해 GSAP 라이브러리를 사용하는데, MPA 방식의 사이트에서는 간단하게 JavaScript CDN만 불러오면 되는데, SPA 라이브러리인 React에서는 너무 설정할 것이 많았고, 매우 복잡하게 설정해야 했다.

그리고 React 라이브러리의 동작 방식이 너무 추상적인지라, 도대체 어떻게 다른 라이브러리를 불러와서 활용하는지에 대한 로직이 내 머릿속으로 시각화되지 않았다. 솔직히 아직도 시각화가 되지 않는다. 도대체 SPA 라이브러리/프레임워크는 어떻게 동작하고 있는 것인가? 프론트엔드 라이브러리/프레임워크 보다 시스템 프로그래밍이 더 이해하기 단순한 거 같다.

다만, 단순함이 쉬움을 의미하지는 않는다.

내가 GitHub에는 공개하지 않았지만, 이 당시 거의 1년 넘게 thisishaneum 버전 수십 개를 만들었었다. 아래의 이미지가 그 기록들이다.

이 이유를 지금에 와서 생각해보면, 완벽주의로 인해 1년 넘개 작업을 지채한 것 같다. 이때의 나에게 『실용주의 프로그래머』의 "완벽한 것을 만들어 내기란 불가능하다"라는 말을 해주는 사람이 있었다면 좋았을 것이다.

이렇게 삽집을 계속 하면서, 이대로는 웹 개발 공부에 진척이 없을 것 같아 thisishaneum을 만드는 것을 포기하게 되었다.

그러나 참 웃긴 것은, 이때 삽질하던 것이 지금 나에게 매우 큰 도움이 되었다는 것이다. 이는, 프론트엔드 프로그래밍이 일개 마크업이라는 것에 대한 증명이다. 프론트엔드 개발 또한 프로그래밍이다. 프론트엔드는 프로그래밍이 아니라는 주장은, 프론트엔드 개발을 '제대로' 해보지 않은 개발자들이 하는 주장일 뿐이다.

thisishaneum.com

GitHub Repo: https://github.com/chebread/thisishaneum

thisishaneum을 개발하는 것을 포기한 후 Next.js가 사이트를 만드는데 아주 편리하다고 해서, Next.js를 배우면서 다시 thisishaneum 사이트를 만드는 것에 도전하게 되었다.

이번에는 나는 삽질을 최소화하기 위해 다른 개발자분들이 만든 프로젝트들을 참고해서 개발을 진행했다. 블로그 프로그램의 로직은 https://github.com/MaxLeiter/maxleiter.com를 참고해서 개발했고, 블로그의 디자인은 https://tinyclouds.org를 참고해서 개발했다.

다른 것을 참고해서 개발하니 매우 순조롭게 개발이 끝났고, Google Domains로 thisishaneum.com Domain을 구매 후 Cloudflare로 Domain을 연결하고 Vercel에 배포하니, 매우 그럴듯한 블로그가 완성되었다. 내가 창조한 것은 아니지만, 그래도 Haneum Blog 개발 이후 이렇게 제대로 배포해본 거는 오랜만이라 뜻깊게 여겨졌다.

이렇게 thisishaneum.com 블로그를 개발하고 열심히 블로그 활동을 이어가던 중, 하나 눈에 띄는 것을 발견하게 되었다. 바로 나의 thisishaneum.com GitHub Repository의 Folk가 1로 되어 있는 것이다.

누가 Folk를 했을 까 궁금하여 Fork history를 보니 어떤 인도 개발자가 Folk를 한 것을 알게되었다. 그 인도 개발자의 GitHub를 들어가보니 충격을 받게 되었다. 바로 나의 블로그를 그냥 Folk하여, 그대로 자신의 사이트처럼 배포를 해놓고 운영중이었던 것이다. 또한, 내가 한국어로 작성한 공개/비공개 포스팅을 영어로 번역해서 그대로 포스팅하고 있었다. 정말 충격적이었다.

이 사건을 통해 나는 오픈소스를 잘 사용해야 겠다는 생각이 번쩍 들었다. 그 리포지토리는 MIT License를 사용했던 지라 그 개발자를 저작권법으로 신고할 수도 없었으므로, 개인적으로 이메일을 통해 지워잘라고 재차 부탁해서, GitHub에서 만큼은 없애게 되었다.

이 인도 개발자 사태 이후, 사건도 사건이고 블로그 또한 내가 직접 만든 것은 아닌지라 thisishaneum.com 블로그에 대한 애정이 많이 떨어지게 되었다. 그래서 GitHub에 블로그 소스코드는 올려놓는 대신, 배포는 중단하게 되었다.

chebread.github.io

GitHub Repo: https://github.com/chebread/chebread.github.io

인도 개발자 사태 이후 개인 블로그에 대한 애정이 많이 식어서 Velog 활동만 했다. 그러나, 그래도 개발자라면 개인 사이트는 하나 쯤은 가지고 있어야 한다고 생각이 들었다. 그래서 다시 블로그를 개발해봐야 겠다고 생각되어, 2024년 초께 아래와 같은 블로그 디자인을 완성했다.

디자인을 완성한 후에, Next.js로 블로그를 개발하려고 했다. 그러나, 그렇게 계획만 하고 있다가 거의 1년이 지나버렸다. 블로그 개발이 늦어진 여러 이유들이 있겠으나, 고등학교 진학 이후 전반적인 번아웃이 가장 큰 비중을 차지할 것이다.

그렇게 2025년이 되고, 프론트엔드 개발을 포기하고 시스템 프로그래밍을 공부하게 되고, Go 언어를 공부하면서 문득 "Go로 정적 블로그 빌더를 만들면 어떨까?"라는 생각이 들게 되었다.

Go 언어의 이론을 체화하는데 매우 큰 도움이 될 것 같아 블로그 정적 빌더를 만들게 되었다. 블로그 디자인은 이미 만들어 놓은 것을 활용해 순조롭게 스타일링 했고, 블로그 로직 부분은 시대가 시대인지라, 비생산적인 측면이라고 판단되는 부분은 LLM을 사용했고, 핵심적인 로직은 내가 직접 구현했다.

내가 구현한 로직은 여러 로직이 있지만, 몇 가지를 소개해보자면, PostsData를 통한 데이터 중앙화와 GetFilePaths를 클로저 방식으로 구현한 것이다. PostsData 로직은 너무 길어서 첨부하기는 그러므로, GetFilePaths 함수만 첨부하겠다.

func GetFilePaths(dirPath string) []string {
	var files []string
	var f func(string) []string // Closure 함수 타입 선언
	f = func(dirPath string) []string {
		entries, err := os.ReadDir(dirPath)
		if err != nil {
			fmt.Println(err)
		}
		for _, v := range entries {
			if v.IsDir() {
				subDirPath := dirPath + "/" + v.Name()
				f(subDirPath)
			} else {
				if filepath.Ext(v.Name()) == ".md" || filepath.Ext(v.Name()) == ".mdx" {
					files = append(files, dirPath+"/"+v.Name())
				}
			}
		}
		return files
	}
	f(dirPath)
	return files
}

그렇게 재밌게 Go로 정적 블로그를 완성하게 되었고, 그 결과물이 지금 당신이 보고 있는 이 chebread.github.io 블로그이다.

이 블로그의 핵심 기능을 하나 소개 해보자면, 파일명 기반 블로그 제목 및 링크 생성이다. 즉, 파일명이 곧 블로그 제목이다. 파일명에는 한글이 들어가도 상관 없고 특수문자, 한자 등이 들어가도 상관이 없다. 자동으로 이들을 처리해서 링크명을 생성해준다.

굳이 불편하게 마크다운 프론트 메터에서 title로 설정하지 않아도 되며, slug 속성을 지정하지 않아도 된다. 파일명으로 title과 slug를 함께 지정할 수 있다. 이는 기존의 정적 빌더에서는 지원하지 않던 매우 편리한 기능이라고 볼 수 있다.

그러나 이번 프로젝트를 하면서 내가 반성해야 하는 것은, 내가 모르는 Golang 개념이 너무 많았다는 것이다. 그래서 조금은 LLM을 남용한 측면이 있는 것 같다. 아직은 내가 작성한 코드임에도 불구하고, 솔직히 이해하지 못하겠다. TGPL의 Interface 파트 까지는 학습해야 온전히 나의 코드를 이해할 수 있을 듯 하다. Golang을 마스터하여, 나의 블로그 코드 전체를 이해하는 그 날이 꼭 오기를 기원한다.

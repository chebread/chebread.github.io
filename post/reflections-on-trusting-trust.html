논문 요약

Quine

Quine이란 프로그램을 실행하면 그 실행한 프로그램의 소스 코드가 출력되는 프로그램을 말합니다.

Bootstrapping

C 언어로 프로그래밍 했습니다. 그러나, C 컴파일러가 없습니다. 아주 간단한 v1 C 컴파일러를 기계어 또는 어셈블리어로 만듭니다. 기계어 또는 어셈블리어로 만든 v1 C 컴파일러를 이용해 C 언어를 컴파일 할 수 있습니다. 이제 C언어로 더 기능이 많은 v2 C 컴파일러를 만듭니다. 기계어 또는 어셈블리어로 만든 v1 C 컴파일러를 이용해 C언어로 만든 v2 C 컴파일러를 컴파일합니다. C언어로 만든 v2 C 컴파일러가 만들어졌습니다. v2 C 컴파일러는 자기 자신 v2 C 컴파일러를 컴파일하면, C언어로 C 컴파일러를 만들 수 있습니다. 이렇게 'C언어로 C 컴파일러'를 만드는 과정을 'Bootstrapping'이라고 합니다.

바이너리를 통한 지식의 전수

\n을 만나면 11을 반환(if (c == 'n') return 11;)하는 컴파일러 A가 있습니다. n을 만나면 \n을 반환(if (c == 'n') return '\n';)하라고 프로그래밍된 컴파일러 B가 있습니다. A로 컴파일해보면 \n = 11 으로 평가되어 결국 컴파일러 B는 \n = 11 라는 지식이 소스코드에는 없지만, 바이너리를 통해 전수됩니다. 이것이 바이너리를 통한 지식의 전수입니다.

그러나, 다음 컴파일러 C에 n을 처리하는 로직이 없으면 해당 지식이 사라집니다. 이러한 것을 방지하기 위해 컴파일러 X를 만들 때, n를 만나면 11을 반환하라는 로직(if (c == 'n') return 11;)은 있지만, 컴파일러 X를 가지고 다른 컴파일러를 컴파일 하는 경우에 if (c == 'n') return 11; 로직과 이러한 다른 컴파일러를 반환하는 경우에 if (c == 'n') return 11; 를 삽입하라는 로직을 넣어버립니다. 이러한 로직을 Quine이라고 부릅니다. 이러면 X로 어떤 코드를 컴파일할 때 n을 만나면 11을 반환하고, X로 어떤 컴파일러 Y를 컴파일할 때 n = 11 이라는 정보 및 다른 컴파일러를 컴파일할 때 n = 11 이라는 정보를 넣어라는 것을 소스코드에는 보이지 않게 바이너리를 통해 전달하게 됩니다. 그 이후에 컴파일러 Y 바이너리에는 이러한 Quine 로직이 있으나, 그 존재를 바이너리를 까보지 않는 이상 모릅니다. 그리고 컴파일러 Y의 소스코드에는 이러한 지식이 절대로 존재하지 않습니다. 컴파일러 Y를 가지고 컴파일러 Z를 컴파일하는 경우, 이러한 지식이 계속해서 영속적으로 전달되게 됩니다. 근데, n = 11 말고 Backdoor를 넣어버리면, 사용자는 알지 못한체 바이너리를 통해 영속적으로 백도어가 전달되게 됩니다.

근데 바이너리를 통한 지식이 전수 이니까, 바이너리를 까보면 되지 않을까요? 이론적으로는 가능하지만, 현실적으로는 불가능합니다. 현대의 컴파일러 바이너리는 수백 메가바이트에 달하며, 어셈블리어로 변환하면 수억 줄의 코드가 쏟아져 나옵니다. 백도어 바이너리 코드는 이 수억 줄의 바이너리 코든 사이 어딘가에 극단적으로 최적화되고 파편화되어 숨어있습니다. 가장 치명적인 문제는, 우리는 감염되지 않은 '진짜 깨끗한 원본 컴파일러 바이너리'를 세상 그 어디에서도 구할 수 없을 수도 있다는 것입니다. 태초부터 부모 컴파일러가 감염되어 있었을 수도 있으니까요. 비교할 깨끗한 원본이 없으니, 수억 줄의 기계어를 오로지 맨땅에 헤딩하며 분석해야 합니다. 무엇이 정상이고 무엇이 비정상인지 비교할 기준 자체가 존재하지 않기 때문에, 바이너리 분석을 통해 백도어를 찾아내는 것은 사실상 불가능합니다.

결론

우리가 사용하는 컴파일러에 악성코드 및 다른 컴파일러를 컴파일할 경우 악성코드를 심어라 라는 Quine이 있을지는 모릅니다. 이런 악성 컴파일러로 컴파일한 프로그램에 악성코드가 들어갈 수 있습니다. 그러므로 프로그램을 만든 사람을 신뢰해야 합니다. 즉, 프로그램은 신뢰 자체가 불가능합니다.

서론

저는 프로그래머입니다. 세금 신고서 직업란에도 그렇게 적습니다. 프로그래머로서 저는 프로그램을 작성합니다. 저는 오늘 여러분께 제가 작성했던 프로그램 중 가장 "귀여운(cutest)" 프로그램을 소개하고자 합니다. 3단계에 걸쳐 설명하고 마지막에 하나로 종합해 보겠습니다.

서론의 중심 내용은, 어떤 cutest 프로그램을 소개한다는 것입니다. cutest 프로그램을 세 단계로 나눠 발표하고, 마지막에 하나로 종합한다고 합니다.

Stage I

비디오 게임이 없던 대학 시절, 우리는 프로그래밍 문제를 내며 놀곤 했습니다. 가장 인기 있었던 문제 중 하나는 가장 짧은 "자기 복제 프로그램(self-reproducing program)"을 작성하는 것이었습니다. 현실과는 동떨어진 연습이었기에, 주로 사용된 언어는 FORTRAN이었습니다. 사실 FORTRAN이 선택된 이유는 2인 3각 경기가 인기 있는 이유와 같습니다(역주: 다루기 힘들고 제약이 많아 도전적이라는 의미).

더 정확히 말하자면, 이 문제는 컴파일되고 실행되었을 때 자신의 소스 코드를 정확히 복사본으로 출력하는 소스 프로그램을 작성하는 것입니다. 만약 이 작업을 해본 적이 없다면, 스스로 한번 시도해 보기를 강력히 권합니다. 이를 수행하는 방법을 스스로 발견하는 것은, 남에게 정답을 듣는 것보다 훨씬 더 큰 깨달음을 줍니다. "가장 짧은" 코드를 짜는 것은 단지 기술을 뽐내고 승자를 가리기 위한 조건일 뿐입니다.

"컴파일되고 실행되었을 때 자신의 소스 코드를 정확히 복사본으로 출력하는 소스 프로그램"은 "자기 복제 프로그램"의 정의입니다. 즉, 자기 복제 프로그램이란 "실행하면 소스 코드와 100% 똑같은 텍스트가 나오는" 프로그램을 뜻합니다. 컴퓨터 과학 용어로는 자기 복제 프로그램을 콰인(Quine)이라고 부릅니다. 소스코드와 출력이 토씨 하나라도 다르면 콰인이 아닙니다.

켄 톰슨께서 " 만약 이 작업을 해본 적이 없다면, 스스로 한번 시도해 보기를 강력히 권합니다"라고 하셨기에, 저는 자기 복제 프로그램을 Python 언어로 구현해보았습니다.

print("hello")

일단 먼저 가장 기본적인 hello를 출력하는 프로그램을 작성했습니다.

> python main.py
hello

해당 프로그램을 실행해보니 hello라는 출력 결과만 나옵니다. 지금 제가 원하는 것은 자기 자신의 프로그램 코드 자체인 print("hello")를 출력하는 것입니다. 그러나 지금은 hello 출력 결과만 반환합니다.

print("print(\"Hello\")")

그래서 print("hello")를 출력하도록 코드를 고쳐봤습니다.

> python main.py
print("Hello")

제가 원하던 print("Hello") 결과가 나왔지만, 지금 현재 프로그램의 코드는 print("print(\"Hello\")") 이므로 출력 결과와 상이합니다.

print("print(\"print(\"Hello\")\")")

다시 print("print(\"Hello\")") 를 출력하도록 코드를 작성했습니다.

> python main.py
print("print(\"Hello\")")

제가 원하던 결과인 print("print(\"Hello\")") 가 도출되었습니다. 그러나, 지금 현재 프로그램의 코드는 print("print(\"print(\"Hello\")\")") 으로 출력 결과와 상이합니다.

[Figure 1]은 C 프로그래밍 언어로 작성된 자기 복제 프로그램입니다. (엄밀히 말하면 정확한 자기 복제 프로그램이라기보다, 자기 복제 프로그램을 생성하는 프로그램입니다.) 이 코드는 상을 받기에는 너무 크지만, 기술을 시연하는 데는 적절합니다. 그리고 제 이야기를 완성하는 데 필요한 두 가지 중요한 속성을 가지고 있습니다.

  1. 이 프로그램은 다른 프로그램에 의해 쉽게 작성될 수 있습니다.
  2. 이 프로그램은 메인 알고리즘과 함께 복제될 임의의 "군더더기 데이터(excess baggage)"를 포함할 수 있습니다. 예제에서는 주석조차도 복제됩니다.

Figure 1이 자기 복제 프로그램의 예시입니다. Figure 1 코드는 C언어로 작성되어서 어렵게 보일 수 있습니다. 그래서 Go 언어로 Quine 프로그램을 구현하여 Figure 1 코드를 이해해보겠습니다.

package main

import "fmt"

func main() {
	s := "package main\n\nimport \"fmt\"\n\nfunc main() {\n\ts := %q\n\tfmt.Printf(s, s)\n}\n"
	fmt.Printf(s, s)
}

Go로 재작성한 Quine 프로그램에 대해 설명 해드리겠습니다. 해당 프로그램을 go run main.go 명령어로 실행하게 되면 package main... 부터 쭉 실행이 됩니다. 그러다가 fmt.Printf 부분을 만납니다. 해당 코드가 뜻하는 바는 표준 출력(여기서는 터미널)에 출력하는 것입니다. fmt.Printf의 첫 번째 s는 포맷 문자열을 뜻합니다. 포맷 문자열은 직접적으로 표준 출력되는 문자열을 뜻하며, 출력될때 포맷 문자열(여기서는 %q...)에 데이터를 삽입합니다. 그러면 fmt.Printf를 Go 컴파일러가 실행시에 package main\n\nimport \"fmt\"\n\nfunc main() {\n\ts := 를 출력합니다. 그리고 %q가 만나면 두 번째 s를 여기 %q에 넣어서 출력합니다. 참고로, Go 언어에서 %q는 문자열을 따옴표로 감싸진 소스 코드 리터럴 형태로 변환하여 출력합니다. 이 기능 덕분에 켄 톰슨처럼 아스키 코드를 일일이 계산하지 않아도 s 변수의 선언부를 완벽하게 재현할 수 있습니다. %q는 그러나 다시 s 이기 때문에 package main\n\nimport \"fmt\"\n\nfunc main() {\n\ts := %q\n\tfmt.Printf(s, s)\n}\n 를 %q 부분에 넣습니다. 그리고 남은 \n\tfmt.Printf(s, s)\n}\n 부분을 출력합니다. main 함수가 끝났으니 프로그램이 종료됩니다.

이 프로그램의 결과를 보면

> go run main.go
package main

import "fmt"

func main() {
	s := "package main\n\nimport \"fmt\"\n\nfunc main() {\n\ts := %q\n\tfmt.Printf(s, s)\n}\n"
	fmt.Printf(s, s)
}

놀랍게도 제가 작성한 코드와 동일한 코드가 출력되게 됩니다. 즉, Quine 프로그램을 구현한 것입니다.

더불어, 켄 톰슨께서 "이 프로그램은 다른 프로그램에 의해 쉽게 작성될 수 있습니다"라고 하셨기에, 다른 프로그램을 우리도 Go 언어로 만들어봅시다. 저는 이 다른 프로그램을 generator 라고 하겠습니다.

package main

import "fmt"

func main() {
	const skeleton = `package main

import "fmt"

func main() {
	// 군더더기 데이터: 켄 톰슨의 논문처럼 주석을 달아보았습니다.
	// 이 주석도 완벽하게 복제될 것입니다.
	s := %q
	fmt.Printf(s, s)
}
`
	fmt.Printf(skeleton, skeleton)
}


> go run generator.go
package main

import "fmt"

func main() {
	// 군더더기 데이터: 켄 톰슨의 논문처럼 주석을 달아보았습니다.
	// 이 주석도 완벽하게 복제될 것입니다.
	s := "package main\n\nimport \"fmt\"\n\nfunc main() {\n\t// 군더더기 데이터: 켄 톰슨의 논문처럼 주석을 달아보았습니다.\n\t// 이 주석도 완벽하게 복제될 것입니다.\n\ts := %q\n\tfmt.Printf(s, s)\n}\n"
	fmt.Printf(s, s)
}

이 프로그램을 출력하면 정말 놀랍게도 우리가 처음에 만든 프로그램이 출력됩니다. 그러나 generator 프로그램 속 skeleton 데이터의 s 변수에는 아까의 코드처럼 코드 전체가 없지요. 즉, 우리가 켄 톰슨이 말한 "다른 프로그램"을 만든 것입니다. 중요한 것은 generator 프로그램은 Quine 프로그램은 아닙니다. generator 프로그램이 생성한 코드가 Quine 프로그램입니다. 즉, generator는 Quine이 아니며, generator가 낳은 자식이 Quine입니다. generator는 Quine을 만드는 도구입니다.

Stage I 요약

Quine이란 프로그램을 실행하면 그 실행한 프로그램의 소스 코드가 출력되는 프로그램을 말합니다.

Stage II

C 컴파일러는 C로 작성되어 있습니다.

C 컴파일러는 C로 작성 되어있다고 합니다. 이것이 어떻게 가능할까요? 어떻게 자기 자신의 언어로 만든 코드를 자기 자신의 언어로 만든 컴파일러로 컴파일할 수 있을까요? 그 이유는, 부트스트래핑이라는 것 때문에 가능합니다.

부트스트래핑에 대해서 한 번 설명해보겠습니다.

  1. C 언어로 프로그래밍 했습니다. 그러나, C 컴파일러가 없습니다.
  2. 아주 간단한 C 컴파일러(v1)를 기계어(또는 어셈블리어)로 짭니다.
  3. v1을 이용해 C 언어를 컴파일 할 수 있습니다.
  4. 이제 C언어로 더 기능이 많은 C 컴파일러(v2)를 만듭니다.
  5. v1 컴파일러를 이용해 C언어로 만든 v2 컴파일러를 컴파일합니다.
  6. C언어로 만든 v2 컴파일러가 만들어졌습니다.
  7. 이제 v2를 이용해 v2 Source를 다시 컴파일하거나, v3를 만듭니다. 이제 C 컴파일러는 자기 자신을 컴파일할 수 있습니다. 이렇게 "C언어로 C 컴파일러"를 만드는 과정을 부트스트래핑이라고 합니다.

Figure 2.1

제가 설명하려는 것은 컴파일러가 자기 자신의 언어로 작성될 때 발생하는 수많은 "닭과 달걀(chicken and egg)" 문제 중 하나입니다. 여기서는 C 컴파일러의 특정 예시를 사용하겠습니다.

/* Figure 2.1: 기존 컴파일러 코드 */
c = next();
if (c != '\\')
    return(c);
c = next();
if (c  '\\')
    return('\\');
if (c  'n')
    return('\n');

[Figure 2.1]은 문자 이스케이프 시퀀스를 해석하는 C 컴파일러 코드를 이상적으로 표현한 것입니다. 이것은 놀라운 코드입니다. 이 코드는 어떤 문자 집합(character set)을 사용하든 줄 바꿈 문자의 코드가 무엇인지 완벽하게 이식성 있는(portable) 방법으로 "알고" 있습니다. 이렇게 알게 된 지식은 컴파일러가 자기 자신을 재컴파일할 때 그대로 전수됩니다.

Figure 2.1 코드에 대해서 이해해봅시다. Figure 2.1 코드는 문자 이스케이프 시퀀스를 해석하여 처리하는 C 컴파일러 코드입니다.

Figure 2.1 코드에 대해서 설명해보자면, 여기서 next() 함수는 문자열을 하나 씩 읽는 함수입니다. Figure 2.1 프로그램을 통해 \n 라는 이스케이프 시퀀스를 읽는다고 가정해봅시다. 참고로, '\\' 는 '\'의 이스케이프 시퀀스이므로, \\는 \를 의미합니다.

c = next() 를 처음 실행하면, c에는 \ 가 들어갈 겁니다. if (c != '\\') return c; 부분은 c가 \ 이기 때문에 \ \ 으로 true 인데, != 이므로 false로 평가되어 실행되지 않고 아래로 넘어가게 됩니다.

c = next() 를 두 번째로 실행하면 c에는 n 가 들어갈 겁니다. if (c '\\') 에서 c는 n 으로 false입니다. false 이므로, 실행되지 않고 아래로 넘어가게 됩니다. if (c 'n') 에서 c는 n 으로 true입니다. true 이므로, return('\n'); 을 반환하게 됩니다.

이스케이프 시퀀스를 처리한다는 것은 컴퓨터가 알아듣게 10, 21 같은 숫자로 변환해야 합니다. 근데 해당 Figure 2.1 코드는 문자 이스케이프 시퀀스를 해석하여 처리하는 C 컴파일러 코드라고 했는데, 왜 이스케이프 시퀀스를 처리하지 않고, 다시 말해 10, 21 같은 숫자를 반환하지 않고\n를 반환했을까요?

"이 코드는 어떤 문자 집합(character set)을 사용하든 줄 바꿈 문자의 코드가 무엇인지 완벽하게 이식성 있는(portable) 방법으로 "알고" 있습니다."

그 이유가 여기에 나와 있습니다. 즉, 이식성 있는 컴파일러를 만들기 위함입니다.

만약, \n 반환하는 방법을 사용하지 않고서 컴파일러를 만든다고 생각해봅시다. A 컴퓨터 (ASCII 방식)는 줄바꿈(\n)을 숫자 10으로 저장합니다. B 컴퓨터 (EBCDIC 방식는 줄바꿈(\n)을 숫자 21로 저장합니다.

if (c  'n') return 10;

이 코드는 A 컴퓨터에서는 잘 돌아갑니다. 하지만 B 컴퓨터에서는 돌아가지 않습니다. 전재조건: X라는 c 컴파일러를 사용하며, X라는 c컴파일러는 10이 줄바꿈임을 알고 있습니다.

if (c  'n') return 21;

그러면 21을 반환하게 해볼까요? 이 코드는 위 코드와 다르게 B 컴퓨터에서는 잘 돌아갑니다. 그러나, 원래 잘 돌아가던 A 컴퓨터에서는 돌아가지 않습니다. 전재조건: Y라는 c 컴파일러를 사용하며, Y라는 c컴파일러는 21이 줄바꿈임을 알고 있습니다.

if (c  'n') return '\n';

이 코드는 위 코드들과 다르게 숫자를 적지 않았습니다. 그냥 "줄바꿈(\n)"이라는 추상적인 기호를 적었습니다.

이 코드를 A 컴퓨터에서 컴파일하면, A 컴퓨터의 기존의 X 컴파일러가 \n을 보고 10으로 바꿔줍니다. 이 코드를 B 컴퓨터에서 컴파일하면, B 컴퓨터의 기존의 Y 컴파일러가 \n을 보고 21로 바꿔줍니다.

주의할 점은, 이 \n을 반환하는 코드는 위 2개 기계어 자체를 반환하는 코드보다 X, Y라는 c 컴파일러에 대한 의존이 매우 높습니다. X, Y 컴파일러가 \n 을 어떻게 처리할지 모르면 아무 소용이 없습니다. 그리고 10을 \n으로 하는 컴퓨터에 21로 반환해버리면 아무 소용이 없습니다. 그러므로, 컴파일러가 \n을 알고 있다는 전제 하에서만 이식성 있는 컴파일러를 만들 수 있습니다. 여기서 말하는 이식성이 있는 컴파일러란, 소스 코드(\n)만 써도 개행 기계어가 반환 되는 것을 의미합니다. 즉, "개발자가 코드를 수정할 필요가 없다"는 뜻에서의 이식성입니다. A, B 컴퓨터 모두의 기계어가 호환된다는 뜻이 아닙니다.

그리고 현대에 와서 X, Y 같은 태초의 컴파일러를 따로 만들지 않아도 되게 된 이유가 크로스 컴파일러의 등장 때문입니다. 크로스 컴파일러는 \n = 10 or 21 or ... 이렇게 운영체제에 맞는 기계어 처리 방식을 모두 다 가지고 있고, 컴파일 할 때 마다 모드를 설정하면 됩니다.

그럼 하나 의문이 생깁니다. \n = 10 or 21을 아는 최초의 컴파일러는 어떻게 만들어야 할까요? 논문의 Figure 2.3이 바로 그 과정을 설명합니다.

" 이렇게 알게 된 지식은 컴파일러가 자기 자신을 재컴파일할 때 그대로 전수됩니다."

이러한 과정을 통해 해당 문장을 이해할 수 있습니다. 여기서 말하는 말의 핵심은 바로 "지식의 전수"입니다. 이미 있는 공식으로 번역(\n = 10, 21)한 걸 가지고 무슨 지식을 물려줬다고 지식의 전수라고 부를 수 있는 이유가 무엇일까요? 소스 코드에 없던 정보가 결과물에 생겼으니까 그렇게 부를 수 있습니다. 이해를 위해 예를 들어보겠습니다.

상황 A: 지식의 출처가 '소스 코드'인 경우 (우리가 아는 상식)

  • 소스: return 10; (여기에 '10'이라는 정보가 있음)
  • 컴파일러: (그냥 읽고 씀)
  • 결과물: 10
  • 분석: 결과물의 10은 소스 코드에서 왔습니다. 지식의 주인 = 소스 코드

상황 B: 지식의 출처가 '컴파일러'인 경우 (켄 톰슨의 논리)

  • 소스: return '\n'; (여기에 '10'이라는 숫자가 있습니까? 없습니다. 그냥 '줄바꿈'이라는 기호만 있습니다.)
  • 컴파일러: "어? \n이네? 내 머릿속(지식)에 있는 10을 꺼내야지."
  • 결과물: 10
  • 분석: 결과물의 10은 어디서 왔나요? 소스 코드에는 절대 없었습니다. 부모 컴파일러의 뇌 속에서 튀어나온 겁니다.

즉, 핵심은 소스 코드에 증거(숫자)를 남기지 않아도, 내(컴파일러)가 알고 있는 정보(지식)를 자식에게 몰래 박아 넣을 수 있다는 겁니다.

Figure 2.2

/* Figure 2.2: 우리가 원하는 최종 코드 (하지만 아직 컴파일 불가) */
c = next();
if (c != '\\')
    return(c);
c = next();
if (c  '\\')
    return('\\');
if (c  'n')
    return('\n');
if (c  'v')
    return('\v'); /* 컴파일러가 \v를 아직 모르므로 에러 발생 */

만약 우리가 수직 탭(vertical tab) 문자를 나타내는 \v 시퀀스를 포함하도록 C 컴파일러를 수정하고 싶다면 어떻게 해야 할까요? [Figure 2.1]을 확장하여 [Figure 2.2]처럼 만드는 것은 뻔한 일입니다. 하지만 이 코드를 컴파일러에 넣고 재컴파일하면 오류(diagnostic)가 발생합니다. 당연하게도, 현재 실행 중인 바이너리 버전의 컴파일러는 \v에 대해 알지 못하므로, 소스 코드에 있는 \v는 합법적인 C 코드가 아니기 때문입니다. 우리는 컴파일러를 "훈련(train)"시켜야 합니다.

이제 Figure 2.2 부분을 이해해봅시다. 지금 Figure 2.2에서 말하는 상황은, 우리가 Figure 2.1에서 발전된, 새로운 \v라는 기능을 추가한 컴파일러를 만들고 싶은 상황입니다. 그러나, 이 부분의 핵심 말은 이거를 부모 컴파일러를 사용하여 컴파일 해도 \v 이부분을 부모 컴파일러가 어떤 숫자로 바꿀지를 모르기 때문에 에러 난다는 겁니다. 그래서 우리는 컴파일러를 "훈련"시켜야 한다는 겁니다.

제가 설명하려는 것은 컴파일러가 자기 자신의 언어로 작성될 때 발생하는 수많은 "닭과 달걀(chicken and egg)" 문제 중 하나입니다.

더불어, 이러한 Figure 2.2의 상황이 논문에서 말한 닭과 달걀 문제 상황입니다.

우리는 지금 C 컴파일러 v1.0(구형)을 가지고 있습니다. 그러나 해당 컴파일러는 \v가 뭔지 모릅니다. 우리는 \v를 아는 C 컴파일러 v2.0(신형)을 만들고 싶습니다. Figure 2.2 소스 코드에 return '\v';라고 적었습니다.

이 소스를 실행 파일로 만들려면 v1.0을 통과시켜야 합니다. v1.0이 소스를 읽다가 \v를 만납니다. v1.0는 \v를 어떻게 처리하는지 모름으로 컴파일 에러를 반환합니다. 결국, v2.0을 만들 수가 없습니다.

왜 이게 닭과 달걀 문제 상황일까요?

먼저 용어부터 정립합시다.

  • 닭 (Chicken): 알을 품어서 생명체로 만드는 존재 -> 컴파일러 (실행 파일/바이너리)
  • 달걀 (Egg): 닭이 될 유전 정보를 담은 설계도 -> 소스 코드 (텍스트)

우리의 목표는 위에서 말했듯 "슈퍼 닭(\v를 아는 컴파일러)"을 얻는 겁니다.

  • 슈퍼 닭(v2.0)을 얻으려면? -> 슈퍼 달걀(\v 소스)을 인큐베이터(컴파일러)에 넣고 돌려야 나옵니다.
  • 그런데 슈퍼 달걀(\v 소스)을 깨서 닭으로 만들려면? -> 그 달걀 껍데기(\v)를 깰 수 있는 슈퍼 닭(v2.0)이 인큐베이터 역할을 해야 합니다. (일반 닭 v1.0은 \v 껍데기를 못 깸)

이렇게 서로가 서로를 필요로 하는데, 둘 다 세상에 없는 상태입니다. "만들려면 도구가 필요한데, 그 도구를 만들려면 그 도구가 필요함." 이 순환 의존성 때문에 닭과 달걀이라고 부르는 겁니다.

근데 이런 의문이 생깁니다. 왜 \v = 11로 숫자 반환 방식을 사용하지 않고 \v 반환 방식을 썼을까요? 그 이유는 위에서 말한 이식성 때문입니다. 만약 소스 코드에 평생 return 11;이라고 적어놓으면, 11이 수직탭으로 설정된 A 컴퓨터(ASCII)에서는 잘 돌아가지만, 11이 수직탭으로 설정되지 않은 B 컴퓨터(EBCDIC)에서는 오류가 발생합니다. 그래서 소스 코드에 return '\v';라고 적은 겁니다. 이렇게 하면 A 컴퓨터든 B 컴퓨터든 알아서 해당 운영체제에 맞는 기계어 처리 숫자로 바뀌니까요. 그러나 여기서 문제는, 이런 이식성이 좋은 컴파일러를 만들고 싶은데, 지금 당장 있는 컴파일러가 멍청해서 \v를 모른다는 것입니다. 그래서 "멋진 소스(\v)를 쓰려면 $\rightarrow$ 똑똑한 컴파일러가 필요함." "똑똑한 컴파일러를 만들려면 $\rightarrow$ 멋진 소스(\v)를 컴파일해야 함." 이라는 닭과 달걀의 문제가 발생한 것입니다. 그래서 이에 대한 해결책이 Figure 2.3의 방식입니다.

Figure 2.3

/* Figure 2.3: 부트스트래핑을 위한 코드 */
c = next();
if (c != '\\')
    return(c);
c = next();
if (c  '\\')
    return('\\');
if (c  'n')
    return('\n');
if (c  'v')
    return(11); /* 11은 수직 탭의 ASCII 값. 하드코딩하여 가르침 */

컴파일러가 \v의 의미를 알게 된 후에야 우리의 새로운 코드가 합법적인 C가 됩니다. 우리는 ASCII 표를 찾아보고 수직 탭이 10진수 11임을 확인합니다. 그리고 소스를 [Figure 2.3]처럼 수정합니다. 이제 기존 컴파일러는 이 새로운 소스를 받아들입니다. 이렇게 생성된 바이너리를 새로운 공식 C 컴파일러로 설치하고 나면, 우리는 비로소 [Figure 2.2]와 같이 이식성 있는 버전으로 소스를 작성할 수 있게 됩니다.

이것은 매우 심오한 개념입니다. 이것은 제가 본 것 중 가장 "학습(learning)" 프로그램에 근접한 것입니다. 단 한 번만 알려주면, 그 이후로는 자기 참조적인 정의를 사용할 수 있게 됩니다.

우리는 컴파일러를 "훈련(train)"시켜야 합니다.

Figure 2.3 예제는 이 논문에서 말한 "훈련"시키는 과정을 설명하고 있습니다. 즉, \v를 사용해도 괜찮은, 이식성이 좋은 컴파일러를 만드는 법을 설명하고 있습니다.

이제 Figure 2.3 예제로 하여금, \v 를 아는 컴파일러를 \v 를 모르는 부모 컴파일러로 하여금 만드는 방법을 설명해보겠습니다.

참고로, 해당 figure 2.3 같은 코드를 컴파일한다는 것은 return은 MOV로, 11 같은 것은 기계어로 코드 자체를 기계어로 번역하는 것을 의미합니다. 코드의 실행이 아닙니다.

참고로, 11을 반환하는 것은 부모 컴파일러도 허용해줍니다. \v 같은 것을 반환해서 11로 치환하는 것을 부모 컴파일러가 모른다는 거지, 11을 반환하는 것을 모른다는 것은 아닙니다. 11을 반환하라고 하면 기계어로 잘 반환해줍니다. 11은 숫자일 뿐이니까요.

그러나, 부모 컴파일러는 11이 수직 탭인지 뭔지 의미는 전혀 모릅니다. Figure 2.3은 11을 반환하는 컴파일러를 만든겁니다. 그러면 이게 \v을 처리하는 컴파일러를 만들게 됩니다. 이제 이 figure 2.3으로 \v을 처리하면 11로 반환됩니다. 11이 이미 정의된 ascii니까 컴퓨터로 반환하면 컴퓨터는 수직탭임을 이미 압니다.

Figure 2.3이 어떻게 Figure 2.2의 닭과 달걀의 문제를 해결한 것일까요? 닭과 달걀 문제의 핵심은 "소스 코드에 \v를 쓰고 싶은데, 컴파일러가 \v를 모른다"는 것이었습니다. 우리는 방금 만든 이 '11을 아는 컴파일러'를 이용해, 실패했던 Figure 2.2의 소스 코드(return '\v';)를 다시 컴파일할 수 있게 되었기 때문입니다. 이전의 부모 컴파일러는 \v를 몰라서 이 소스를 거부했지만, 숫자 11로 훈련된 새로운 컴파일러는 \v가 11임을 알기 때문에 이 소스를 받아들입니다. 즉, "숫자(11)라는 임시 다리"를 놓아서, "소스 코드(\v)와 컴파일러 사이의 끊어진 고리"를 연결한 것입니다. 이것이 켄 톰슨이 닭과 달걀의 문제를 해결한 방식입니다.

논문의 Figure 2.3은 \v(수직 탭)를 예시로 들고 있지만, 사실 이 과정은 우리가 당연하게 여기는 \n(줄바꿈)이 최초에 어떻게 컴파일러에게 주입되었는지를 보여주기도 합니다. "그럼 \n = 10을 아는 최초의 컴파일러는 도대체 어떻게 만들어졌을까요?" 정답은 위에서 살펴본 Figure 2.3과 똑같습니다. 태초의 개발자는 Figure 2.3 처럼 그냥 숫자를 사용했습니다.

태초에는 세상에 \n을 아는 컴파일러가 없습니다. 개발자가 소스 코드에 return 10;(ASCII 기준)이라고 숫자를 직접 적어서, 당시의 원시적인 컴파일러(혹은 어셈블러)에게 줍니다. 이렇게 만들어진 최초의 C 컴파일러(A)는 뱃속에 10이라는 정보를 기계어로 갖게 됩니다. 이제 소스 코드의 10을 지우고 return '\n';으로 고칩니다. 하지만 A 컴파일러가 살아있는 한, 그 자식들은 영원히 10을 물려받습니다. 즉, Figure 2.3은 \v를 가르치는 과정임과 동시에, 과거에 \n이 어떻게 컴파일러에게 주입되었는지를 알려주는 과정입니다.

제가 컴파일러에 심은 실제 버그는 UNIX의 login 명령 소스 코드와 매칭되었습니다. 이 대체 코드는 login 명령을 잘못 컴파일하여, 원래 의도된 암호화된 비밀번호뿐만 아니라 특정하게 알려진 비밀번호도 받아들이도록 만들었습니다. 따라서 이 코드가 컴파일러 바이너리에 설치되고, 그 컴파일러로 login 명령을 컴파일했다면, 저는 그 시스템에 어떤 사용자로든 로그인할 수 있게 됩니다.

하지만 이런 노골적인 코드는 오래 숨길 수 없습니다. C 컴파일러 소스를 조금만 훑어봐도 의심을 살 것입니다.

이제부터 매우 어렵습니다. 논문 한 문장씩 차근차근 이해 해봅시다.

[Figure 3.2]는 특정 패턴이 매치될 때마다 소스를 고의적으로 잘못 컴파일하도록 컴파일러를 수정한 것입니다.

Figure 3.2 상황은, C 컴파일러를 이용해서 유닉스(Unix) 운영체제 전체를 빌드(컴파일)하고 있는, 운영체제 안에 수많은 프로그램을 컴파일하는 상황입니다.

compile("login_backdoor"); 이 부분이 고의적으로 잘못 컴파일하도록 한 겁니다. 정상적인 컴파일러라면 들어온 소스 코드 s를 컴파일해야 합니다. 그러나 이 컴파일러(Figure 3.2)는 켄 톰슨이 미리 준비해둔 악성 코드 문자열("login_backdoor")을 대신 컴파일해서 집어넣습니다. 그러나, s를 컴파일 하지 않는 것은 아닙니다. 원래 s를 컴파일하는 것은 login_backdoor 안에 포함되어 있습니다. 이것이 바로 "고의적으로 잘못 컴파일하도록 수정한 것"입니다. s를 컴파일 하지 않으면, login 프로그램이 로그인을 못 하게 되어 고장 나고, 해킹은 즉시 발각됩니다. 그러므로 꼭 s를 컴파일 해야 합니다.

만약 이것이 고의가 아니었다면 "컴파일러 버그"라고 불렀을 것입니다. 하지만 고의적이므로 이것은 "트로이 목마(Trojan horse)"라고 불러야 합니다.

이렇게 악의적으로 컴파일을 하는 것을 트로이 목마라고 합니다. 왜 이렇게 악의적으로 컴파일 하는 것을 트로이 목마라고 부를 까요? 겉모습은 유용한 "C 컴파일러"입니다. 속내는 특정 상황이 되면 튀어나와서 시스템을 망가뜨리는 "병사(악성 코드 삽입기)"가 숨어 있습니다. 겉과 속이 다르기 때문에 트로이 목마라고 부릅니다. 즉, 겉과 속이 다른 것을 트로이 목마라고 합니다.

제가 컴파일러에 심은 실제 버그는 UNIX의 login 명령 소스 코드와 매칭되었습니다.

이 말은 if(match(s, "login_pattern")) 이거를 뜻하는 겁니다. 켄 톰슨은 모든 프로그램을 해킹하고 싶은 게 아닙니다. login 프로그램만 노립니다. 그래서 컴파일러가 소스 코드를 읽다가 "어? 지금 내가 컴파일하고 있는 게 login.c 파일이네?"라고 감지하는 부분이 바로 이 코드입니다. 어떻게 감지를 하냐고요? 그거는 login_pattern으로 감지합니다. 예를 들어, login 프로그램 코드에서만 사용되는 어떤 코드가 있을 겁니다. 그거를 login_pattern으로 상정하고 감지하는 겁니다.

이 대체 코드는 login 명령을 잘못 컴파일하여, 원래 의도된 암호화된 비밀번호뿐만 아니라 특정하게 알려진 비밀번호도 받아들이도록 만들었습니다. 따라서 이 코드가 컴파일러 바이너리에 설치되고, 그 컴파일러로 login 명령을 컴파일했다면, 저는 그 시스템에 어떤 사용자로든 로그인할 수 있게 됩니다.

즉, compile("login_backdoor")를 실행하여 login_backdoor 라는 C언어 악성코드를 기존 login 프로그램 코드에 삽입해서 함께 컴파일합니다. login_backdoor의 역할은 "원래 의도된 암호화된 비밀번호뿐만 아니라 특정하게 알려진 비밀번호도 받아들이도록" 하는 것입니다. 즉, ID마다 부여된 PW 뿐 만 아니라, master PW를 설정한 것입니다. 이렇게 되면 "어떤 사용자로든 로그인할 수" 있게 됩니다. 관리자 권한이 필요할 때는 id: root, pw: foo 로 로그인이 가능하며, ElonMusk 계정을 보고 싶을 때는 id: ElonMusk, pw: foo로 로그인이 가능합니다. 즉, 켄 톰슨의 백도어는 "특정 비밀번호를 입력하면, 아까 입력한 ID가 누구든지 간에 무조건 통과시켜라"는 로직입니다.

하지만 이런 노골적인 코드는 오래 숨길 수 없습니다. C 컴파일러 소스를 조금만 훑어봐도 의심을 살 것입니다.

사람들이 compile("login_backdoor") 코드만 봐도 백도어라고 쓰여 있으니까 바로 안다는 겁니다. 여기서 말하는 백도어란, 정상적인 인증 절차를 거치지 않고 시스템에 몰래 침입할 수 있는 비밀 통로를 의미합니다.

누군가 C 컴파일러의 소스 코드(compiler.c)를 열어봤는데, 아래처럼 적혀 있다고 생각해봅시다.

if (match(s, "login.c")) {
    compile("해킹코드_삽입"); // 누가 봐도 수상함!
}

개발자라면 이걸 보자마자 바로 삭제해 버릴 겁니다. 그래서 켄 톰슨은 고민했습니다. "아... 이 나쁜 짓(Figure 3.2)을 계속하고 싶은데, 소스 코드에 적어두면 금방 들키네? 그렇다면... 이 나쁜 짓을 하는 코드를 소스 코드에서는 지워버리고, 컴파일러의 뇌(바이너리) 속에만 몰래 심을 수 없을까?"

즉, figure 3.2 방식은 컴파일할 소스코드에 새로운 악성 소스 코드를 넣어서 함께 컴파일하는 건데, 이렇게 하면 바로 들통이 납니다. 로직이 노출되니까요. 켄 톰슨은 이거를 방지하고 싶었던 겁니다. 소스 코드에는 안보이는데, 실행 파일에는 해당 기능을 담당하는 소스 코드(login backdoor)가 있어서 백도어를 사용할 수 있게 하고 싶었습니다. 즉, 켄 톰슨의 목표는 "소스 코드는 깨끗한데, 결과물은 오염시킬 수는 없는가"입니다.

  3. 이제 컴파일러 소스 코드에서 버그를 제거합니다.
  4. 하지만 새로운 바이너리 컴파일러가 (깨끗한 소스를) 컴파일할 때마다, 탐지 로직에 의해 버그를 다시 삽입하게 됩니다.

교훈

교훈은 명백합니다. 당신이 직접 작성하지 않은 코드는 신뢰할 수 없습니다. (특히 저 같은 사람을 고용한 회사에서 만든 코드는 더욱 그렇습니다.) 아무리 소스 레벨에서 검증하고 감시한다 해도, 신뢰할 수 없는 코드(컴파일러 등)를 사용하는 한 당신은 보호받을 수 없습니다.

논문 한 문장씩 이해해봅시다.

당신이 직접 작성하지 않은 코드는 신뢰할 수 없습니다.

"코드를 신뢰한다"라는 말은 "이 소스 코드대로 프로그램이 돌아갈 것이다"라는 인과관계를 믿는 것입니다. 그러나, 위에서 보았듯이 소스 코드는 더 이상 프로그램의 동작을 보증하는 설계도가 아닙니다. 소스 코드를 컴파일하는 컴파일러가 오염된 순간, "소스 코드가 깨끗하다"는 사실은 아무런 효력이 없습니다. 결과적으로, 소스 코드가 아무리 깨끗해도, 이걸 컴파일해서 나온 바이너리를 믿을 수 없으니 "이 코드도 믿을 수 없는 존재"나 마찬가지가 된다는 말입니다. 그래서 "코드는 신뢰할 수 없다"고 말한 것입니다.

소스 레벨에서 검증하고 감시한다 해도 신뢰할 수 없는 코드(컴파일러 등)를 사용하는 한 당신은 보호받을 수 없습니다.

소스 코드는 텍스트일 뿐이며, 컴퓨터는 텍스트를 실행하지 못합니다. 텍스트를 컴파일한 기계어 바이너리 파일만 컴퓨터가 실행할 수 있습니다. 그러므로, 텍스트만 깨끗하다고 해도 컴파일러가 깨끗하지 못하면 악성코드는 실행되게 됩니다.

이 공격의 가능성을 보여주기 위해 저는 C 컴파일러를 예로 들었습니다. 하지만 어셈블러, 로더, 심지어 하드웨어 마이크로코드와 같이 프로그램을 처리하는 어떤 프로그램이라도 표적이 될 수 있습니다. 프로그램의 레벨이 낮아질수록, 이러한 버그는 탐지하기가 점점 더 어려워집니다. 잘 설치된 마이크로코드 버그는 탐지가 거의 불가능할 것입니다.

이 말은 "밑으로 내려갈수록 잡아내기가 더 힘들다"는 뜻입니다. 잡아내기 힘들다는 것을 궁극적으로 마이크로코드를 말하고 있습니다. 마이크로코드(Microcode)란 프로세서를 조종하는, 즉 기계어를 보고 프로세서를 위한 전기 신호를 만들어내는 저수준의 소프트웨어 프로그램(펌웨어)입니다. 즉, 기계어를 전기신호로 프로세서에게 보내는 역할을 하는 프로그램을 마이크로코드라고 합니다. 그리고 이런 종류의 프로그램을 펌웨어라고 합니다. 참고로, CPU, GPU, NPU, TPU, ... 모두 본질적으로는 프로세서일 뿐입니다.

여기서 언급되는 HW, SW, FW 용어가 햇갈릴 수 있다. 이 용어에 대해서는 아래에서 설명합니다.

  • 하드웨어 (Hardware): Hard(단단하다). 망치로 때려야 부서지는 물리적인 기계. 한번 만들면 절대 못 바꿉니다.
  • 소프트웨어 (Software): Soft(부드럽다). 언제든지 지우고 다시 깔 수 있는 프로그램.
  • 펌웨어 (Firmware): Firm(견고하다/굳어있다). 소프트웨어긴 한데, 하드웨어에 찰싹 달라붙어서 잘 안 바뀝니다. 하지만 업데이트는 할 수 있습니다. 그래서 "하드(Hard)와 소프트(Soft)의 중간 성격"이라서 펌웨어라고 부릅니다.

즉, 켄 톰슨은 "소프트웨어 엔지니어가 아무리 노력해도, 하드웨어(CPU) 자체가 배신 때리면 답이 없다"는 궁극의 허무함을 이야기하고 있습니다.

제가 신뢰할 수 없는 사람이라는 것을 납득시키려 노력했으니, 이제 설교를 좀 하고 싶습니다. 저는 "해커들(hackers)", 414 갱단, 달튼 갱단 등을 다루는 언론의 태도를 비판하고 싶습니다. 이 아이들이 저지른 행위는 좋게 봐도 공공 기물 파손(vandalism)이고, 나쁘게 보면 무단 침입이자 절도입니다. 해커들이 심각한 기소를 면하는 유일한 이유는 형법이 적절치 못하기 때문입니다. 이런 활동에 취약한 회사들(대부분의 대기업이 매우 취약합니다)은 형법 개정을 강력히 요구하고 있습니다. 컴퓨터 시스템에 대한 무단 접속은 이미 몇몇 주에서 중범죄이며, 의회뿐만 아니라 더 많은 주 의회에서 다뤄지고 있습니다. 폭발적인 상황이 끓어오르고 있습니다. 한편으로는 언론, TV, 영화가 이들을 컴퓨터 신동(whiz kids)이라 부르며 영웅으로 만듭니다. 다른 한편으로는, 이 아이들의 행위는 곧 수년의 징역형을 받을 수 있는 범죄가 될 것입니다. 저는 아이들이 의회에서 증언하는 것을 보았습니다. 그들이 자신의 절도 행위가 얼마나 심각한지 전혀 인지하지 못하고 있다는 것이 분명했습니다. 여기에는 명백한 문화적 차이(gap)가 존재합니다. 컴퓨터 시스템을 침입하는 행위는 이웃집을 침입하는 것과 똑같은 사회적 낙인이 찍혀야 합니다. 이웃집 문이 잠겨있지 않았다는 것은 중요하지 않습니다. 언론은 컴퓨터를 잘못 사용하는 것이 음주 운전만큼이나 놀라울 것 없는(비난받아야 할) 일이라는 것을 배워야 합니다.

켄 톰슨은 앞에서 "내가 마음만 먹으면 전 세계 컴퓨터를 눈치도 못 채게 장악할 수 있다"는 것을 증명했습니다. 그런데 당시 언론은 고작 비밀번호 몇 개 알아내서 남의 회사 서버에 침입하는 철없는 10대들(414 갱단 등)을 보고 "컴퓨터 천재(Whiz kids)", "해커"라며 치켜세우고 있었습니다. 켄 톰슨의 입장에선 기가 찰 노릇이었습니다. "보세요, 제가 방금 보여드린 게 진짜 해킹(창조적이고 치명적인 기술)입니다. 저 아이들이 하는 건 해킹이 아니라, 그냥 남의 집 창문 깨고 들어가는 '좀도둑질(Vandalism)'일 뿐입니다."라고 켄 톰슨은 말하고 싶었습니다.

기술적으로 완벽한 보안은 불가능하다라는 Trusting Trust에 대해서 앞에서 이야기 했습니다. 그래서 기술로 못 막는다면? 사회적 합의인 "법과 윤리"로 막아야 한다고 주장하는 부분이 해당 부분입니다. 즉, "본질적으로 기술적 방어막은 뚫려있으니, 법적/윤리적 방어막이라도 빨리 세워라"라고 말하는 강력한 경고입니다.

본질적으로 기술적 방어막은 뚫려있으니, 법적/윤리적 방어막이라도 빨리 만들어야 합니다.

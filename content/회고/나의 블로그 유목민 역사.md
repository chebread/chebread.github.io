## Velog
> Link: https://velog.io/@haneum

Velog에는 댓글 기능이 자체적으로 탑재되어 있어서 독자들과 상호작용을 할 수 있었다.
그래서 2022년에 Velog를 개설하고 포스팅을 하기 시작했다.

내가 처음으로 쓴 [힙하게 코딩하는 방법](https://velog.io/@haneum/%ED%9E%99%ED%95%98%EA%B2%8C-%EC%BD%94%EB%94%A9%ED%95%98%EB%8A%94-%EB%B0%A9%EB%B2%95) 포스팅이 게시한 지

글 작성 당시에는 중학생이었어서, 비판적인 댓글에 대해서 불쾌함을 느껴 반박하는 댓글도 남기기도 했다.

그 이후, 나는 지속적으로 개발을 하면서 비판에 대한 생각이 긍정적으로 바뀌게 되었다.
개발자에게 비판이란 인격 모독이 아니라 나를 성장케 하는 양분이라는 것을 알게 되었다.

## Haneum Blog
> GitHub Repo: https://github.com/chebread/haneum-blog

Velog에서 활동을 하게 되면서 많은 개발자분들의 Velog를 많이 보게 되었다.
Velog를 보면서 다수의 개발자분들이 개인 사이트를 가지고 계신다는 사실을 알게 되었다.
그래서 나는 나를 소개하는 웹 사이트의 필요성에 대해서 지각하게 되었다.

그 당시 나는 React를 통해 SPA(Single Page Application)를 배우고 있었다.
React 자체는 매우 쉬웠지만, SPA의 핵심 동작 방식은 잘 알지 못했다.
SPA의 핵심 동작과 ES6의 문법도 익힐 겸 Haneum Blog라는 개인 블로그를 직접 만들어보기로 했다.

이 블로그를 개발할 때는 SPA를 직접 구축하는 것이 목표다 보니,
CRA(Create React App)의 도움을 받지 못했으므로 직접 이렇게 Webpack과 Babel을 구성했었다.
지금은 Vite 같은 도구들이 워낙 잘 나오는 편이라 이런 웹 개발 환경을 구성하는 것이 매우 생소할 수 있으나,
그땐 그랬다.

```js
const config = webpackConfig('production');
const configWithSmp = new SpeedMeasurePlugin().wrap(config);
configWithSmp.plugins.push(
  new MiniCssExtractPlugin({
    filename: '[name].[hash:8].css',
    chunkFilename: '[name].[hash:8].chunk.css',
  })
);
const compiler = webpack(configWithSmp);
fs.emptyDirSync(paths.appBuild);
fs.copySync(paths.appPublic, paths.appBuild, {
  dereference: true,
  filter: file => file !== paths.appHtml,
});
const build = () => {
  compiler.run();
};
build();
```

그리고 이렇게 `window` 객체를 활용해서 SPA 라우터를 구현해 보기도 했다.

```js
import routes from './routes.js';
import render from './render.js';

const router = path => {
  if (!(path === window.location.pathname)) {
    window.history.pushState(null, null, window.location.origin + path);
  }
  if (!routes[path]) {
    if (!(path === '/')) {
      render('/404');
    }
    return;
  }
  render(path);
  window.onpopstate = () => {
    if (!routes[window.location.pathname]) {
      if (!(window.location.pathname === '/')) {
        render('/404');
      }
      return;
    }
    render(window.location.pathname);
  };
};

export default router;
```

SPA를 구현하는 데 있어서, 라우터가 가장 구현하기 힘들었다.
라우터가 SPA의 핵심이었으므로, 일단 라우터가 만들어져야 SPA 사이트를 만들 수 있었다.
그래서 거의 몇 주 동안은 라우터만 개발하고 개선했던 거 같다.
그 당시에는 JavaScript도 잘 익히지 못했던 터라, 구현하는데 정말 힘들었다.
SPA를 직접 개발하면서, SPA 프레임워크/라이브러리를 쓰는 이유를 몸소 알게 되었다.

이렇게 나는 항상 이론을 배우면 실전을 바로 병행해 보는 편이다.
이론만 공부한다면, 실전에서 어떻게 이론을 활용해야 하는지 감도 오지 않는다.
쳇바퀴처럼 이론만 공부하는 사람이 되어 버린다.
그러나 실전만 한다면, 또 이론은 알지 못한다.
실전만 하다가 언제부터 이론의 필요성을 느껴 이론을 공부하게 되면
너무 어려운 탓에 이론 공부를 도외시하게 되기 십상이다.
그래서 내가 추천하는 방법은 이론과 실전을 병행하는 것이다.
Haneum Blog도 SPA를 공부하기 위해 진행한 프로젝트이고,
정적 사이트 빌더도 Go 언어의 슬라이스를 익히고자 진행한 프로젝트이다.
여담이지만, 난 어렸을 때 레고를 참 좋아했는데
레고 설명서를 보고 일단 만든 후 부숴버리고 새로운 걸 창작하는 것을 참 좋아했다.
이러한 내 유년 시절의 경향성이, 지금 이렇게 프로그래밍에서도 발현되는듯하다.

## thisishaneum
나는 블로그라는 성격에 국한된 사이트보다는, 나를 표현하는 개인 사이트가 있었으면 좋겠다는 생각이 들었다.
그래서 Haneum Blog 블로그 운영을 중단하고, thisishaneum라는 새로운 개인 사이트를 만들게 되었다.

그 당시 나는 React를 학습하고 있었으므로 React를 기반하여 thisishaneum를 만들게 되었다.
그러나, React로 이 사이트를 만드는 것은 매우 어려움이 많았다.
Horizontal scroll을 구현하기 위해
GSAP 라이브러리를 사용하는데,
MPA 방식의 사이트에서는 간단하게 JavaScript CDN만 불러오면 되는데,
SPA 라이브러리인 React에서는 너무 설정할 것이 많았고, 매우 복잡하게 설정해야 했다.

그리고 React 라이브러리의 동작 방식이 너무 추상적인지라,
도대체 어떻게 다른 라이브러리를 불러와서 활용하는지에 대한 로직이
내 머릿속으로 시각화되지 않았다.
솔직히 아직도 시각화가 되지 않는다.
도대체 SPA 라이브러리/프레임워크는 어떻게 동작하고 있는 것인가?
프론트엔드 라이브러리/프레임워크 보다 시스템 프로그래밍이 더 이해하기 단순한 거 같다.

내가 GitHub에는 공개하지 않았지만,
이 당시 거의 1년 넘게 thisishaneum 버전 수십 개를 만들었었다.
아래의 이미지가 그 기록들이다.

<img src="/assets/thisishaneum-history.webp" width="300">

이 이유를 지금에 와서 생각해 보면, 완벽주의로 인해 1년 넘게 작업을 지 채 한 것 같다.
이때의 나에게 『실용주의 프로그래머』의 "완벽한 것을 만들어 내기란 불가능하다"라는
말을 해주는 사람이 있었다면 좋았을 것이다.

이렇게 삼 집을 계속하면서, 이대로는 웹 개발 공부에 진척이 없을 것 같아
thisishaneum을 만드는 것을 포기하게 되었다.

그러나 참 웃긴 것은, 이때 삽질하던 것이 지금 나에게 매우 큰 도움이 되었다는 것이다.
이는, 프론트엔드 프로그래밍이 일개 마크업이라는 것에 대한 반증이다.
프론트엔드 개발 또한 프로그래밍이다.
프론트엔드는 프로그래밍이 아니라는 주장은,
프론트엔드 개발을 '제대로' 해보지 않은 개발자들이 하는 주장일 뿐이다.

## chebread.github.io
> GitHub Repo: https://github.com/chebread/chebread.github.io

인도 개발자 사태 이후 개인 블로그에 대한 애정이 많이 식어서 Velog 활동만 했다.
그러나, 그래도 개발자라면 개인 사이트는 하나쯤은 가지고 있어야 한다고 생각이 들었다.
그래서 다시 블로그를 개발해 봐야겠다고 생각되어, 2024년 초께 아래와 같은 블로그 디자인을 완성했다.

디자인을 완성한 후에, Next.js로 블로그를 개발하려고 했다.
그러나, 그렇게 계획만 하고 있다가 거의 1년이 지나버렸다.
블로그 개발이 늦어진 여러 이유들이 있겠으나,
고등학교 진학 이후 전반적인 번아웃이 가장 큰 비중을 차지할 것이다.

그렇게 2025년이 되고,
프론트엔드 개발을 포기하고 시스템 프로그래밍을 공부하게 되고,
Go 언어를 공부하면서 문득 "Go로 정적 블로그 빌더를 만들면 어떨까?"라는 생각이 들게 되었다.

Go 언어의 이론을 체화하는데 매우 큰 도움이 될 것 같아 블로그 정적 빌더를 만들게 되었다.
블로그 디자인은 이미 만들어 놓은 것을 활용해 순조롭게 스타일링 했고,
블로그 로직 부분은 시대가 시대인지라, 비생산적인 측면이라고 판단되는 부분은
LLM을 사용했고, 핵심적인 로직은 내가 직접 구현했다.

내가 구현한 로직은 여러 로직이 있지만,
몇 가지를 소개해 보자면, `PostsData`를 통한 데이터 중앙화와 `GetFilePaths`를 클로저 방식으로 구현한 것이다.
`PostsData` 로직은 너무 길어서 첨부하기는 그러므로, `GetFilePaths` 함수만 첨부하겠다.

```go
func GetFilePaths(dirPath string) []string {
	var files []string
	var f func(string) []string // Closure 함수 타입 선언
	f = func(dirPath string) []string {
		entries, err := os.ReadDir(dirPath)
		if err != nil {
			fmt.Println(err)
		}
		for _, v := range entries {
			if v.IsDir() {
				subDirPath := dirPath + "/" + v.Name()
				f(subDirPath)
			} else {
				if filepath.Ext(v.Name()) == ".md" || filepath.Ext(v.Name()) == ".mdx" {
					files = append(files, dirPath+"/"+v.Name())
				}
			}
		}
		return files
	}
	f(dirPath)
	return files
}
```

그렇게 재밌게 Go로 정적 블로그를 완성하게 되었고,
그 결과물이 지금 당신이 보고 있는 이 [chebread.github.io](https://chebread.github.io/) 블로그이다.

이 블로그의 핵심 기능을 하나 소개해 보자면,
파일명 기반 블로그 제목 및 링크 생성이다.
즉, 파일명이 곧 블로그 제목이다.
파일명에는 한글이 들어가도 상관없고 특수문자, 한자 등이 들어가도 상관이 없다.
자동으로 이들을 처리해서 링크 면을 생성해 준다.

굳이 불편하게 마크다운 프론트 메터에서 `title`로 설정하지 않아도 되며,
`slug` 속성을 지정하지 않아도 된다.
파일명으로 `title`과 `slug`를 함께 지정할 수 있다.
이는 기존의 정적 빌더에서는 지원하지 않던 매우 편리한 기능이라고 볼 수 있다.

그러나 이번 프로젝트를 하면서 내가 반성해야 하는 것은,
내가 모르는 Go 언어의 개념이 너무 많았다는 것이다.
그래서 조금은 LLM을 남용한 측면이 있는 것 같다.
아직은 내가 작성한 코드임에도 불구하고, 솔직히 이해하지 못하겠다.
TGPL의 Interface 파트까지는 학습해야 온전히 나의 코드를 이해할 수 있을 듯하다.
Go 언어를 마스터하여, 나의 블로그 코드 전체를 이해하는 그날이 꼭 오기를 기원한다.
